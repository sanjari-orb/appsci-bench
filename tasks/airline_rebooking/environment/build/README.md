# Airline BUILD-phase seed store

The data the **build phase** of a run loads: a small synthetic airline the AppSci agent explores while it
elicits requirements and builds its artifact. The **eval phase** keeps the full store at
`../../db/` — 300 flights, 500 users, 2000 reservations — and that is what the artifact is scored
against.

This file sits **beside** `data/` rather than inside it on purpose. A phase declaration bundles its
data directory into the container, so anything in `data/` is agent-visible -- and this README names the
eval store, the split, and the fact that the environment is replaced, none of which the agent is told
(`docs/task_env_carve_spec.md`). A stray README in an agent-mounted directory has already leaked
`eval_data/` and `gold/` once in this repo; keeping documentation one level up avoids repeating it.

Generated by `scripts/generate_airline_build_seed.py`. Do not hand-edit: re-run the script instead, which
validates the result and refuses to write a store the tools cannot use.

| File | What it is |
|------|------------|
| `db.json` | The whole store, `{flights, users, reservations}`. **The only file the environment reads** (`AirlineDB.load`). |
| `flights.json` / `users.json` / `reservations.json` | The three collections split out, for inspection. Never loaded — they mirror the eval fixture's layout so both halves read the same way. |

Contents: **10 flights** over 5 airports (DEN, JFK, LAX, ORD, SFO) with all 30 dates of the eval store's
May-2024 window, **5 users** (two gold, two silver, one regular), **10 reservations**.

## Why it exists

During the build phase the agent can read every record in its environment — through the airline tools or
by writing its own client. The 50 eval cases are drawn from the real store, so an agent that reads that
store can shape its artifact around the very rows it will be scored on, and a score cannot then separate
"elicited the rules well" from "read the answers off the substrate". Giving the build phase its own data
closes that. See `docs/task_env_split.md` for the mechanism and `docs/task_env_carve_spec.md` for the
wider plan.

## Synthetic, not a carve — and what that costs

The carve spec calls for a referentially closed **subset** of the real store. This store is generated
instead. Two properties get stronger and one gets weaker:

- **Disjointness is structural.** A carve must prove it excluded all 34 customers and 118 flights the eval
  cases touch; fresh identifiers cannot collide at all. Verified anyway, against both the eval store's keys
  and the identifier tokens its 50 cases name.
- **Category coverage is authored.** A strict carve leaves ~1% of bookings — "one of everything and many of
  nothing". Here every enumerated value is placed deliberately: all three cabins, both trip types, both
  insurance values, all three membership tiers, all three payment sources, both card brands, and all six
  flight statuses.
- **Scale is lost, and this is the real trade.** 10 reservations against 2000; 5 airports against 20. An
  artifact that caches `list_all_airports`, or assumes a store this small, will be wrong at eval. That is
  arguably the generalisation pressure the split exists to create — but it is a behaviour change a carve
  would not have introduced, so it is the first thing to suspect if eval scores move.

## What the records are shaped to support

The store is small but not simplified: every field the eval store carries is present, with the same names
and nesting, so the agent learns the real schema. Reservations cover the situations the airline policy
turns on — one already flown (transfer only), one basic economy (flights unmodifiable), one business
(cancellable on cabin alone), one booked inside the 24-hour window, one on an airline-cancelled flight
(compensation), a two-leg itinerary, and parties of one through four.

The clock is fixed at `2024-05-15T15:00:00`, so dates before the 15th have flown, the 15th itself is
in progress, and the 16th onward is bookable. ORD is the hub, which is what makes a connecting
SFO→ORD→JFK trip constructible — relevant because `search_onestop_flight` only aliases the direct
search, so a connection has to be found with two direct searches.

## Not yet live

**The build phase does not load this store yet.** The environment service reads its fixture eagerly at
boot and the harness copies a phase's files in *after* the container is already running, so a bundled
fixture arrives too late. Making it live needs the service to boot empty with a token-gated load command,
the Dockerfile to stop baking `db.json`, and a setup script per phase — steps 5–8 of the carve spec. Until
then these files are inert and every run still loads the full store in both phases.
