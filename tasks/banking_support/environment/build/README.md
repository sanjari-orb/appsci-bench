# Banking BUILD-phase share

The transactional records the **build phase** of a run loads, and the only records the AppSci agent ever
meets while it elicits requirements and builds its artifact. Two things, kept deliberately distinct:

1. the **residue of a strict carve-out** — 8 real records, everything the 97 eval cases do not touch;
2. **100 authored synthetic records** hanging off those same customers, which invent nothing that exists
   in the eval environment.

The **eval phase** keeps the task's full store, and that is what the artifact is scored against.

This file sits **beside** `data/` rather than inside it on purpose. A phase declaration bundles its data
directory into the container, so anything in `data/` is agent-visible — and this README names the split,
the withheld volume, and the fact that the environment is replaced, none of which the agent is told.
A stray README in an agent-mounted directory has already leaked held-out material once in this repo;
keeping documentation one level up avoids repeating it.

Generated by `scripts/generate_banking_build_share.py` from the eval store plus the authored records in
`scripts/banking_build_synthetic.py`. **Do not hand-edit either output file** — re-run the script, which
re-derives the carve from the eval cases, merges the authored records, validates the result, and refuses
to write a share that is not closed, not disjoint, or not the agreed size. `--check` validates and reports
without writing, and fails if what is on disk is not what the script produces; that is how a reviewer
confirms the files still regenerate.

| File | What it is |
|------|------------|
| `data/db.json` | The whole share, in the store's own shape: 17 collections, each `{data, notes}`. The only file the environment loads. |
| `data/expected_counts.json` | Per-collection record counts, asserted by `../setup/setup.sh` after the load. A flat mapping of name to integer, deliberately — anything richer would be read as records by the carve checker. |

## What it holds

**108 records: 8 carved and 100 authored.** The carved 8 are 6 customers and 2 bank accounts, both of the
latter belonging to one customer. The authored 100 give the other five customers accounts, cards,
transactions and history, so every one of the 17 collections in this file now holds something.
(`data/expected_counts.json` lists 23 rather than 17: the data model declares six collections this store
has never used, and the manifest reports what the service reports.) The field documentation each collection
carries is copied across unchanged, because the agent exploring this environment reads that prose as the
schema.

| | Carved (real) | Authored (synthetic) |
|---|---|---|
| users | 6 | — |
| accounts | 2 | 11 |
| debit_cards | — | 8 |
| credit_card_accounts | — | 7 |
| bank_account_transaction_history | — | 29 |
| credit_card_transaction_history | — | 18 |
| payment_history | — | 7 |
| referrals | — | 6 |
| verification_history | — | 3 |
| credit_card_closure_reasons / credit_card_orders / credit_limit_increase_requests | — | 2 each |
| credit_card_applications / cash_back_disputes / transaction_disputes / debit_card_orders / credit_card_account_flags | — | 1 each |

The five runtime bookkeeping collections stay empty on purpose: `agent_discoverable_tools` is the read-log
table the state hash counts, and its keys are a deterministic function of a tool name, so a seeded row
there would both collide with a minted id and move the hash. Those tables are written by a run, not by a
fixture.

## Why the carve is this small, and why that is not a defect

During the build phase the agent can read every record in its environment — through the banking tools or
by writing its own client. The 97 eval cases are drawn from the full store, so an agent that reads that
store can shape its artifact around the very rows it will be scored on, and a score cannot then separate
"elicited the rules well" from "read the answers off the substrate". Withholding those records closes it.

The rule is: withhold every record any eval case touches, add the two records a case is about only in its
prose (below), then close over the reference graph so nothing kept points at something withheld. On this
store that withholds 760 of 768 records. **32 of the 39 customers are touched by name**, and the store is
a hub-and-spoke around customers — 17 reference edges, almost all of them terminating on a customer — so
withholding a customer withholds their accounts, cards, transactions, referrals, disputes and payment
history with them. Nothing is exempt: reference-looking records go too when a case touches them.

**That rule is unchanged and is not to be relaxed.** The synthetic records are not a larger carve; they are
a separate stage that runs after it, with its own validations, and the carve's own residue is still
asserted at 8 so an augmentation can never mask a carve that started leaking.

## Why there are authored records at all

The 8-record carve is the right answer to "which real records may the agent see" and the wrong answer to
"can the agent test its own work". It was measured, not guessed: on run
`banking_support_b1_l3_20260910_023628` the agent's own eval generator wrote a debit-card freeze case
against an invented customer, because the store held no card to freeze and no customer who owned one. Its
judge prompt says so outright — *"the persona uses plausible demo identifiers rather than a shared mutable
record"* — so it graded the conversation instead of the outcome, scored itself 0.9175, and the artifact then
scored 0.021 on the real eval. An agent that cannot build a state-based test builds a politeness test, and
its internal score stops predicting anything.

Each of the six customers now carries one situation an internal eval case can be built from, chosen to
reach past identity verification into the specialist-tool path the eval actually scores:

### The five rules an authored record must obey

All five are enforced by `validate_synthetic` in the generator, so a breach is a refusal to write:

1. **No key may exist in the full store.** This is what "does not belong to the eval environment" means
   operationally — not merely that a record is unscored, but that its id is not the eval store's to reuse.
2. **No key may be named by an eval case**, on whole-value matching, the same test the carve applies.
3. **No key may collide with an id a golden action mints**, or a live creation during scoring would be
   indistinguishable from the starting state.
4. **Every reference must resolve inside the build share** — a carved record or another authored one,
   never anything withheld, and never a key that exists nowhere.
5. **Nothing may be dated after the environment's fixed now** (2025-11-14 03:40:00 EST). Card expiry is
   the deliberate exception and is checked to be in the future instead.

On top of those, the generator checks the things that make the records *sound* rather than merely
well-formed: that each is keyed by its own declared id, that any customer detail it restates matches that
customer's carved row exactly, that card secrets are unique, and that the two accounts young enough for
their whole life to fit inside the transaction window sum to the balance their record states.

## What it still costs

The agent sees a plausible six-customer bank, not the real distribution: **it cannot learn fault patterns,
category mixes or real-world proportions from this store**, because 108 records chosen to cover situations
are not a sample of 768. Volume, frequency and co-occurrence are all wrong by construction, and an artifact
tuned to what is common *here* is tuned to nothing. Schema and mechanism it can now learn from data;
statistics it still cannot, and those must come from the stakeholders.

**Score comparisons for this task must not straddle this change,** for the same reason they must not
straddle the carve itself.

Category coverage went from zero to most of the way. Ten of the eighteen enumerations the spec's
`task_runner.carve.coverage_waiver` used to name are now genuinely covered — both account classes and all
twelve levels, every bank-transaction type, both credit limits, both closure reasons, both replacement-order
reasons, and every debit-card status and issue reason. The **8 that remain waived** are the ones that cannot
be closed without copying the eval customers' own identities into the build store — card secrets, printed
cardholder names, verification contact details, a shipping address — plus the card-type mix in the
transaction history, where covering every value would mean six customers holding eleven credit cards.

## Two records withheld by eye, which the automated derivation cannot see

The carve matches record keys as whole values, which is what stops the short customer ids `123` and `125`
being "found" inside zip codes and amounts — and is also exactly why an identity a case claims in *prose*
is invisible to it. Two records the derivation kept are named that way, and both are now withheld:

- **Customer `125` (Ayan Wang)**, whom `tau2_banking_34` is about: its brief opens "You are Ayan Wang, a
  Rho-Bank customer (user_id: 125). You have a Green Account checking account.", and that sentence is the
  only place the id occurs in the file. Her two bank accounts and her debit card leave with her.
- **Card application `f1a2b3c4d5e6f789`**, whose `customer_name` is Wei Chen, whom `tau2_banking_10` is
  about. It carries no customer id at all, so closure has no edge to follow to it even with her customer
  row withheld — the link exists only in a person's name.

Neither is scored *off*: no golden action mutates either record. They are withheld because an eval case is
*about* them, which is what case-bearing means here. Both are recorded in `WITHHELD_BY_EYE` in
`scripts/generate_banking_build_share.py`, with the case id and the reason per record, and they are seeded
INTO the closure rather than deleted from its output — so the dependents of customer `125` leave through
the ordinary reference rule and no cascade is written down anywhere to drift out of step with the data.

## What is NOT carved

The knowledge base. Both phases hold the same documents and the corpus stays baked into the image, so
neither phase bundles it. 46 of the 48 specialized tools are named **only** by documents the eval cases
require, so withholding those documents would not make the task harder — it would make it unsolvable and
would silently gut the retrieval metric. The corpus is read-only by construction (retrieval never touches
the transactional store) and contains no record identifier from the store at all, so sharing it leaks
nothing the carve protects. The residual exposure is that a *list* of required documents is close to an
answer key; the protection is keeping that list out of any agent-facing artifact, not carving the corpus.
